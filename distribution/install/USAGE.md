# Using Please (TM Edition)

Please (TM Edition) focuses on two improvements to the upstream Please VS Code
extension:

1. **Dynamic BUILD CodeLenses** discover the real targets generated by a BUILD
   rule and create actions for those targets.
2. **Coverage overlays** run the relevant Please coverage targets and show the
   resulting covered and uncovered lines in the editor.

These features are independent. Dynamic CodeLenses operate on BUILD files;
coverage overlays operate on Go source files and Go or Python test files.

The upstream extension also contains other behavior, including debug support
and actions above individual test functions. Those features were not introduced
by this edition and are outside the scope of this guide.

## Prerequisites

Open VS Code at the Please repository root: the directory containing
`.plzconfig`. The extension activates when it finds that file.

Make sure:

- `plz` and `python3` are available on `PATH`.
- VS Code's `editor.codeLens` setting is enabled.
- BUILD files are named `BUILD`, `BUILD.plz`, or `BUILD.build`.

The examples below use this repository structure:

```text
calculator/
├── domain/
│   ├── BUILD
│   ├── calculator.go
│   └── calculator_test.go
└── sat/
    ├── BUILD
    ├── addition_test.go
    └── subtraction_test.go
```

The two features use this structure differently, so each section explains its
own Please queries and editor behavior.

## Feature 1: Dynamic BUILD CodeLenses

### The problem this feature solves

A normal Please rule usually creates a target whose label can be read directly
from the BUILD file. For example:

```python
go_test(
    name = "calculator_test",
    srcs = ["calculator_test.go"],
    deps = [":calculator"],
)
```

The directory containing the BUILD file is the package, and `name` identifies
the target within that package. If the file is `calculator/domain/BUILD`, the
target is:

```text
//calculator/domain:calculator_test
```

Custom build definitions can behave differently. One rule call can generate
several targets and may not create the unsuffixed label at all:

```python
variant_go_test(
    name = "calculator_sat_test",
    variants = [
        "addition",
        "subtraction",
    ],
    deps = ["//calculator/domain:calculator"],
)
```

Assume `variant_go_test` expands this call into:

```text
//calculator/sat:calculator_sat_test_addition
//calculator/sat:calculator_sat_test_subtraction
```

There is no `//calculator/sat:calculator_sat_test` target to test. A CodeLens
that constructs only the label written in the BUILD file would therefore run
the wrong command.

### How dynamic discovery works

For each BUILD rule, the extension parses:

- the rule function, such as `variant_go_test`;
- the `name`, such as `calculator_sat_test`;
- the BUILD package, such as `//calculator/sat`.

It combines the package and name into a base label:

```text
//calculator/sat:calculator_sat_test
```

For rule function names ending in `_test` or `_binary`, the extension asks
Please which labels complete that base label:

```text
$ plz query completions //calculator/sat:calculator_sat_test
//calculator/sat:calculator_sat_test_addition
//calculator/sat:calculator_sat_test_subtraction
```

It then creates one action for each returned target. In this example the two
test CodeLenses run the equivalent of:

```text
plz test --rerun //calculator/sat:calculator_sat_test_addition
plz test --rerun //calculator/sat:calculator_sat_test_subtraction
```

The important change is the target behind each action. The CodeLens uses the
labels returned by Please instead of assuming that the BUILD rule's base label
is executable.

You may also see copy, build, or other CodeLenses supplied by the upstream
extension. Their presence does not mean that they are part of dynamic target
discovery.

### Adding dynamic actions for custom rule names

Automatic discovery applies to rule function names ending in `_test` or
`_binary`. A custom rule that follows neither convention can be configured in
workspace `settings.json`.

Suppose this BUILD rule:

```python
container_image(
    name = "payments",
)
```

has these Please completions:

```text
//services/payments:payments
//services/payments:payments_push
//services/payments:payments_tar
```

The following configuration creates an action for the discovered `_push`
target and one for the known `_tar` target:

```jsonc
{
  "please": {
    "container_image": {
      "code_lens": [
        {
          "title": "plz run push",
          "command": "plz run",
          "postfix_target_filter": "_push"
        },
        {
          "title": "plz build tar",
          "command": "plz build",
          "postfix_target": "_tar"
        }
      ]
    }
  }
}
```

The outer key must match the BUILD rule function name exactly. In this case it
is `container_image`, not the target name `payments`.

Use the fields as follows:

| Field                   | Purpose                                                         |
| ----------------------- | --------------------------------------------------------------- |
| `title`                 | Text shown by VS Code above the BUILD rule                      |
| `command`               | Please command run when the action is clicked                   |
| `postfix_target`        | Append a known suffix to the base label                         |
| `postfix_target_filter` | Query completions and keep generated labels matching the filter |
| `arguments`             | Add command arguments; `${target}` refers to the resolved label |

Use `postfix_target` when the generated names are a stable part of the build
definition's contract. It also accepts an array:

```jsonc
{
  "title": "build package",
  "command": "plz build",
  "postfix_target": ["_linux", "_darwin"]
}
```

Use `postfix_target_filter` when Please should remain the source of truth. The
extension runs `plz query completions` and creates an action for every matching
label.

For example, command arguments can use the resolved target:

```jsonc
{
  "title": "show integration output",
  "command": "plz test",
  "postfix_target": "_integration_test",
  "arguments": ["--show_output", "${target}"]
}
```

For a base label `//services/payments:payments`, this resolves to:

```text
plz test --show_output //services/payments:payments_integration_test
```

Custom settings add actions; they do not remove or replace CodeLenses already
provided by the extension.

### Troubleshooting dynamic CodeLenses

If a generated target action is missing:

1. Confirm that VS Code is open at the repository root containing `.plzconfig`.
2. Confirm `python3` is on `PATH`; it is used to parse BUILD rule calls.
3. Construct the base label from the BUILD package and `name`.
4. Run `plz query completions <base-label>` and check that Please returns the
   expected generated labels.
5. For a configured action, confirm the setting key exactly matches the rule
   function name and the filter matches the returned labels.
6. Check the **Please** Output channel for parsing or query errors.

## Feature 2: Coverage overlays

### The problem this feature solves

Please calculates coverage by test target, but a developer normally starts
from the implementation file being inspected. The coverage feature maps that
file to its owning Please target, finds the relevant tests, runs `plz cover`,
and projects `coverage.json` back onto the editor.

This feature does not depend on the dynamic BUILD CodeLens configuration.
Coverage target selection uses Please ownership and dependency queries.

### Coverage from an implementation file

Assume `calculator/domain/BUILD` contains:

```python
go_library(
    name = "calculator",
    srcs = ["calculator.go"],
    visibility = ["//calculator/..."],
)

go_test(
    name = "calculator_test",
    srcs = ["calculator_test.go"],
    deps = [":calculator"],
)
```

The SAT rule shown earlier also depends directly on
`//calculator/domain:calculator`. When `calculator/domain/calculator.go` is
open, clicking `plz cover` first finds the target that owns the file:

```text
$ plz query whatinputs calculator/domain/calculator.go
//calculator/domain:calculator
```

It then finds direct reverse dependencies:

```text
$ plz query revdeps //calculator/domain:calculator --level=1
//calculator/domain:calculator_test
//calculator/sat:calculator_sat_test_addition
//calculator/sat:calculator_sat_test_subtraction
```

The extension queries metadata for those labels and keeps only test targets
that have not set `no_test_coverage`. It runs one aggregate command:

```text
plz cover \
  //calculator/domain:calculator_test \
  //calculator/sat:calculator_sat_test_addition \
  //calculator/sat:calculator_sat_test_subtraction
```

Tests can therefore contribute to the same implementation file from different
packages, as long as their targets are direct dependants of the source target.
The aggregate command is what combines their coverage into one report.

To cover only one of the eligible targets, open the Command Palette and run
**Please: Cover Current File with Target...**.

### Coverage from a test file

When a test file is open, the extension finds the test target that directly
owns that file. For example:

```text
$ plz query whatinputs calculator/sat/addition_test.go
//calculator/sat:calculator_sat_test_addition
```

Clicking `plz cover` in that test file covers the returned test target. It does
not perform the implementation-file reverse-dependency search.

This distinction is useful:

- Use `plz cover` in an implementation file for aggregate coverage from all
  direct test dependants.
- Use `plz cover` in a test file for a focused run of the target owning that
  test file.

### How the overlay is produced

Please writes coverage results to:

```text
plz-out/log/coverage.json
```

The extension waits for a newer report, reads its per-file line statuses, and
applies them to open editors:

- Green means the line was covered.
- Red means the line was coverable but was not covered.
- Hover text lists the targets that covered the line and the targets that
  reported it uncovered.
- The status bar shows the covered-line percentage for the active file, or a
  workspace summary when the active file has no result.

To remove the visual overlay:

- click `[clear]` next to the file-level coverage action;
- click the coverage item in the status bar; or
- run **Please: Clear Coverage** from the Command Palette or editor context
  menu.

Clearing removes the extension's current decorations. It does not delete
`plz-out/log/coverage.json`, so reopening or reloading the extension may load
the existing report again.

### Coverage boundaries

- Automatic implementation-file discovery follows direct reverse dependencies
  only because it uses `--level=1`.
- Test targets marked `no_test_coverage` are excluded.
- A new `plz cover` command produces a new Please report. Run coverage from the
  implementation file when several direct test targets must be combined.
- The file-level coverage action appears on Go implementation files and on Go
  or Python test files. Ordinary Python implementation files do not receive
  one.
- The visualization shows line coverage, not branch, condition, path, or
  mutation coverage.

### Troubleshooting coverage overlays

If `plz cover` cannot find targets:

1. Run `plz query whatinputs <workspace-relative-file>`.
2. For a Go implementation file, run
   `plz query revdeps <source-target> --level=1`.
3. Confirm that the expected tests directly depend on the source target.
4. Confirm each candidate is a test target and does not set
   `no_test_coverage`.

If the command succeeds but no colours appear:

1. Confirm `plz-out/log/coverage.json` was created or updated by that run.
2. Confirm the report contains the open file under its workspace-relative
   path.
3. Check the **Please** Output channel for report parsing or monitoring errors.
4. Run **Developer: Reload Window** only as a diagnostic. A normal successful
   coverage run should refresh without a reload.

## Starter `settings.json`

These settings enable CodeLenses and send Please commands to an integrated
terminal:

```jsonc
{
  "editor.codeLens": true,
  "please.runInTerminal": true,
  "plz.trace.server": "off"
}
```

`please.runInTerminal` affects commands launched by the extension. It does not
change how dynamic targets are discovered or how coverage targets are
selected.

Add the top-level `please` object only when custom BUILD rules need extra
dynamic actions:

```jsonc
{
  "editor.codeLens": true,
  "please.runInTerminal": true,
  "plz.trace.server": "off",

  "please": {
    "container_image": {
      "code_lens": [
        {
          "title": "plz run push",
          "command": "plz run",
          "postfix_target_filter": "_push"
        }
      ]
    }
  }
}
```

Coverage overlays currently have no separate `settings.json` configuration.
They use the Please ownership and dependency graph described above.
